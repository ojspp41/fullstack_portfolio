> **담당 범위:** 열린 소켓의 인증 토큰 교체를 프론트와 Gateway에서 구현했습니다. 재연결 뒤 현재 세션의 저장 이력과 답변 순서를 맞추는 화면은 팀이 만든 서버 복구 기록에 연결했습니다.

## 문제 원인 · 해결 목표

- **상황:** 중복 연결, 이전 소켓의 이벤트, 숨김 탭 종료로 응답이 끊겼습니다. 청크마다 화면을 갱신하면 폭주 시 렌더링 부담도 커졌습니다.
- **목표:** 중복 송신과 스트리밍 손실을 막고, 정상 속도의 응답을 유지하면서 폭주 패턴의 불필요한 화면 갱신을 줄여야 했습니다.

## 해결 과정

1. Heartbeat, 지수 백오프와 Jitter를 적용하고, 연결 가드와 세대 확인으로 중복 연결·이전 소켓 이벤트를 차단했습니다. 인증 실패에는 재연결을 중단했습니다.
2. 숨김 탭은 **5분 뒤 유휴 연결만 종료**하고 스트리밍 중에는 유지했습니다. 활성 세션 설정의 중복 송신도 막았습니다.
3. 짧은 3ms 구간으로 청크를 묶어 반영하고 마지막 응답은 누락 없이 반영했습니다. 폭주·혼합·정상 패턴을 따로 측정했습니다.

## 결과

| React Profiler 입력 패턴 | 변경 전 | 변경 후 |
|---|---|---|
| 폭주 · 500개 청크 | 500회 | 2회 · 99.6% 감소 |
| 혼합 패턴 | 200회 | 100회 |
| 정상 패턴 | 60회 | 60회 |

### 검증 조건 · 현재 한계

99.6%는 과거 고정 폭주 패턴의 React Profiler 기록입니다. 당시 원자료와 현재 구현의 정확한 대응은 확인되지 않았습니다. 정상 패턴은 같은 횟수를 유지했고, 네트워크 지연·사용자 체감 시간·전체 서비스 처리량을 측정한 결과는 아닙니다.

### 재연결 뒤 첫 질문의 접수 확인

연결이 돌아와도 첫 질문이 접수됐는지는 알 수 없습니다. 후속 브랜치에서 전송마다 요청 ID를 남기고, 확인 응답(ACK)을 놓치면 같은 ID로 접수 상태를 조회하도록 했습니다. Gateway는 접수 기록과 대기 작업을 함께 저장한 뒤 응답합니다.

로컬 Gateway 두 개에서 ACK 유실, 같은 ID 동시 전송, 저장 직후 프로세스 종료를 각 20회 재현했습니다. 60회 모두 사용자 메시지·실행 진입·답변 저장이 한 번씩 기록됐습니다. 모델은 고정 응답을 사용했습니다.

화면 갱신은 별개 실험입니다. 1ms 간격으로 500조각을 보냈을 때 16ms 버퍼로 저장소 쓰기는 500회에서 24회로 줄었고, 수신 후 화면 반영 p95는 19.7ms에서 33.9ms로 늘었습니다.
