## 전체적인 아키텍처

![권한을 유지한 채팅 목록 조회 최적화 — 전체 구조](/diagrams/query.png)

*구조 그림을 선택하면 원본 크기로 볼 수 있습니다.*

> **담당 범위:** Go 목록 조회·권한 확인·복합 인덱스와 FE 로딩 상태를 개선했습니다. 성능은 로컬 조회 구간에서 측정했습니다.

## 문제 원인 · 해결 목표 (S·T)

- **상황(S):** 목록 8개를 보여주기 전에 전체 허용 ID와 메시지 본문을 읽었습니다. 프론트는 조회가 끝나기 전에도 빈 목록 안내를 표시했습니다.
- **목표(T):** 기존 권한·반환 결과를 유지하면서 조회 비용을 줄이고, 현재 조회가 끝난 후에만 빈 상태를 보여줘야 했습니다.

## 해결 과정 (A)

1. 목록에 필요한 필드만 projection으로 읽고 메시지 본문을 제외했습니다. 전체 허용 ID 수집을 읽기 제외 후보의 유효 권한 재검증으로 바꿨습니다.
2. 사용자·조직·최신순 목록과 제외 후보 조회에 맞는 복합 인덱스를 추가했습니다. 같은 인덱스 조건의 대조군도 측정해 조회 구조 변경의 효과를 분리했습니다.
3. 내 채팅·공유 채팅의 로딩 상태를 나누고, 현재 요청이 끝난 뒤에만 빈 결과를 표시했습니다. 성능 측정과 별개로 반환 ID·합계·필터 결과의 동등성을 확인했습니다.

## 결과 (R)

- **약 1.4만 건 로컬 데이터, 목록+필터 합산 p95:** 378.36ms → 18.72ms, 약 95.1% 감소.
- **200회 응답 비교:** 반환 결과 digest가 일치했고 fixture 문서가 변경되지 않았습니다.

### 검증 조건 · 현재 한계

Apple M5·MongoDB 8.0.28·Go 1.24.5의 warmed 로컬 환경에서 AB/BA 순서로 비교했습니다. 동시성 1, 기본 첫 페이지 정렬, 단일 조직·사용자·에이전트의 합성 데이터입니다. HTTP·인증·네트워크·프론트 렌더링과 인덱스 생성 비용은 제외했습니다. 전체 권한 회귀나 운영 응답시간 개선율로 확대하지 않습니다.
