# 파일 인앱 미리보기

**풀스택 · 보안**

- 기술: Go(Gin) · MinIO · DRM · Next.js 15 · React 19 · TypeScript · DOMPurify

사내 보안 파일을 원본 노출과 능동형 콘텐츠의 무분별한 실행 없이 인앱으로 미리보는 파이프라인입니다. 서버가 DRM 처리 사본만 격리 정책과 함께 내려줍니다.

### BE — 통로 분리 & 서버 강제 격리

- 다운로드/미리보기 엔드포인트를 대칭 분리
  - 다운로드: 원본을 첨부(`attachment`)로 서빙
  - 미리보기: DRM 사본만 인라인(`inline`)으로 서빙
- 미리보기 경로는 원본 저장소를 참조조차 하지 않도록 설계
- “원본은 미리보기로 새지 않는다”를 테스트로 고정
- 파일을 통째로 메모리에 올리지 않고 스트리밍 전달
- 접근 시 파일 읽기 권한 재검증
- 경로 우회(path-traversal) 차단
- 능동형 콘텐츠(HTML·SVG·XML)는 서버가 격리 정책(CSP sandbox + MIME 스니핑 차단)을 강제
- 서버가 실질 신뢰 경계

### 오피스 문서 PDF 선생성 흐름과 현재 경계

PPTX·HWP·HWPX는 Gateway가 미리보기 요청을 받을 때 변환하지 않습니다. 파싱엔진이 원본 처리 과정에서 `{ObjectName}.pdf` 키로 파생 PDF를 MinIO에 미리 생성하고, Gateway는 파일 읽기 권한과 `%PDF` 유효성을 검사한 뒤 해당 객체를 스트리밍합니다.

덮어쓰기에서는 원본 저장을 핵심 기능, 파생 PDF 정리를 복구 가능한 부가 작업으로 구분했습니다. 기존 파생 PDF 삭제가 실패해도 정상 원본 업로드까지 실패시키지는 않고 `preview_pdf_cleanup_failed` 오류 로그를 남깁니다. 다만 현재 구현은 이 파생 PDF 삭제 실패를 영속 재시도 큐에 직접 기록하지 않습니다. 새 파싱도 실패하면 이전 PDF가 같은 키에 남을 수 있으며, Gateway는 현재 처리 시도에서 생성한 PDF인지 확인하지 않기 때문에 오래된 미리보기를 내려줄 가능성이 있습니다.

현재 Gateway는 문서 처리 실패를 자동으로 다시 발행하지 않고 즉시 실패로 기록합니다. 수동 재시도 API는 존재하지만 현재 연결된 클라이언트는 없습니다. 프론트도 파일의 처리 상태가 아니라 지원 형식과 읽기 권한으로 미리보기 진입을 결정하므로, PDF가 없으면 미리보기 실패 후 다운로드 안내를 보여주고 이전 PDF가 남아 있으면 오래된 내용을 표시할 수 있습니다.

보완하려면 처리 상태에 따라 `처리 중 → 미리보기 비활성화`, `실패 → 실패 안내와 재시도`, `PDF 준비 완료 → 미리보기 활성화`로 화면을 연결해야 합니다. 오래된 PDF 노출까지 막으려면 화면 변경만으로는 부족하며, 파싱 시도 번호와 파생 PDF 생성 번호를 함께 기록하고 Gateway가 둘의 일치 여부를 검증하는 서비스 간 계약이 필요합니다.

### 영속 재시도 큐 보강 설계

현재 RAG 이벤트 발행 경로에는 DB에 작업을 먼저 저장하고 별도 worker가 처리하는 `system_outbox`와 처리 세대를 구분하는 `processing_attempt_id`가 이미 있습니다. 다만 이 기반은 파생 PDF 삭제 실패를 직접 재시도하지 않으므로, `PREVIEW_PDF_CLEANUP` 작업 유형을 추가해 파일 변경과 같은 트랜잭션에서 정리 작업을 영속 저장하는 방향으로 설계했습니다. 작업에는 `event_id`, `file_id`, `organization_id`, `object_key`, `source_processing_attempt_id`, `status`, `attempt_count`, `next_retry_at`, `last_error`를 기록하고, worker는 실패할 때마다 다음 실행 시각을 늦춰 재시도하며 한도를 넘긴 작업은 별도 실패 상태로 격리합니다.

재시작 뒤에도 작업이 남도록 DB를 큐로 사용하고, 동일 작업이 반복 실행돼도 결과가 달라지지 않도록 `event_id` 기반 중복 방지를 적용합니다. 오래된 작업이 최신 결과를 지우거나 덮어쓰지 못하게 worker와 Gateway가 현재 파일의 `processing_attempt_id`와 작업·파생 PDF의 처리 번호가 일치하는지 확인합니다. 더 강하게 격리하려면 파생 객체 키도 `{ObjectName}.{processing_attempt_id}.pdf`처럼 세대별로 분리하고, PDF 생성 완료가 확인된 세대만 미리보기 대상으로 선택한 뒤 과거 객체를 비동기로 정리합니다. 이 내용은 기존 구현 결과가 아니라 현재 코드의 `system_outbox`·`processing_attempt_id` 기반을 확장하는 후속 보강 설계입니다.

### FE — 단일 파이프라인 & 자원 정리

- 형식 판별(확장자 → MIME 폴백) 후 6종을 하나의 렌더링 파이프라인으로 처리
- 미지원 형식은 자동 다운로드 안내
- 미리보기용 임시 데이터·진행 중 요청을 모든 종료 경로에서 정리(누수 0)
- 능동형 콘텐츠는 살균(DOMPurify) + 분리 프레임(iframe sandbox)으로 2차 방어
- PDF는 툴바·다운로드 숨김
- 미리보기 모듈은 실제로 열 때만 로드(코드 분할)

### 핵심 성과 · 신규 형식 추가 비용 = 매퍼 한 줄

| 지표 | 결과 | 검증 |
|---|---:|---|
| 원본 노출 | 0 | BE 테스트 |
| 임시 데이터 누수 | 0 | FE 테스트 |
| 능동형 콘텐츠 실행 방어 | 3단계 | 서버 1 + 화면 2 |

### Gateway PDF 처리 경로 로컬 벤치마크

과거 요청 시 변환 구조는 문서 엔진이 반환한 PDF를 `io.ReadAll`로 전부 `[]byte`에 적재한 뒤 캐시에 저장했습니다. 현재 구조는 파싱엔진이 MinIO에 미리 생성한 PDF의 `%PDF` 4바이트만 검사하고, 검사에 소비한 바이트를 `io.MultiReader`로 복원해 그대로 스트리밍합니다.

Apple M5 · Go 1.24.5 환경에서 동일한 PDF 바이트를 대상으로 각 경로를 3회 측정한 중앙값입니다.

| PDF 크기 | 과거 전체 버퍼링 | 현재 검증·스트리밍 | 내부 처리시간 변화 |
|---:|---:|---:|---:|
| 1 MiB | 300µs · 5,241,208B 할당(약 5.00 MiB) | 15.1µs · 228B 할당 | 약 19.8배 |
| 10 MiB | 1.59ms · 52,263,356B 할당(약 49.84 MiB) | 154.5µs · 229B 할당 | 약 10.3배 |
| 50 MiB | 8.31ms · 314,628,741B 할당(약 300.05 MiB) | 813.9µs · 234B 할당 | 약 10.2배 |

핵심 결과는 파일 크기가 커져도 현재 스트리밍 경로의 요청당 추가 할당량이 약 228~234B로 거의 일정하다는 점입니다. 과거 경로는 `io.ReadAll`의 버퍼 확장 과정에서 PDF 크기보다 많은 누적 메모리를 할당했습니다.

# 파일 인앱 미리보기 — 동시 처리 & 운영 검증

로컬 동시 처리 결과와 운영 환경에서 추가로 채울 지표를 분리해 정리했습니다.

### 동시 처리 벤치마크

10 MiB PDF를 10개 병렬 워커로 10초 동안 반복 처리하고 프로세스 RSS를 50ms 간격으로 샘플링했습니다.

| 조건 | 과거 전체 버퍼링 | 현재 검증·스트리밍 | 변화 |
|---|---:|---:|---|
| 병렬 워커 | 10 | 10 | 동일 |
| 요청당 누적 할당량 | 52,263,249B(약 49.84 MiB) | 228B | 파일 전체 복사 제거 |
| 로컬 테스트 프로세스 최대 RSS | 758,192KiB(약 740.4 MiB) | 54,496KiB(약 53.2 MiB) | 약 92.8% 감소 |

최대 RSS에는 Go 런타임·테스트 코드·공유한 10 MiB 입력 버퍼가 모두 포함됩니다. 운영 Pod 수치가 아니라 동일 머신·동일 부하에서 두 구현을 비교한 로컬 프로세스 측정값입니다.

단일 요청 처리시간 측정 범위는 Gateway 프로세스 내부 CPU 시간과 요청당 누적 할당량입니다. MinIO 네트워크, 권한 조회, 파싱엔진 PDF 생성 시간은 포함하지 않았습니다. 따라서 “사용자 응답이 10배 빨라졌다”가 아니라 다음 결과까지만 확인했습니다.

- 10 MiB 요청당 약 49.84 MiB → 229B
- 10개 병렬 워커 최대 RSS 약 740.4 MiB → 53.2 MiB

BE가 원본/사본 통로를 가르고 서버가 격리를 강제하며, FE는 6종을 단일 파이프라인으로 안전 사본만 렌더하고 자원까지 정리합니다. “원본은 지키고, 안전 사본만, 실수 없이, 가볍게”를 흐름 전체에 일관 적용했습니다. 기존 다운로드는 건드리지 않고 미리보기만 새로 얹었습니다.

### 운영 환경에서 추가 검증할 지표

| 지표 | 측정 시작 → 종료 | 집계 |
|---|---|---|
| 실제 사용자 응답시간 | 브라우저 미리보기 요청 직전 → PDF Viewer load 완료 | 동일 파일 30회 p50·p95 · cold/warm 분리 |
| MinIO 네트워크 지연 | `StatObject` 호출 직전 → 첫 바이트 수신 및 스트림 완료 | stat RTT·TTFB·stream duration 분리 |
| 파싱 완료 후 PDF 준비시간 | 업로드 접수 → PDF 최초 조회 성공 | PPTX·HWP·HWPX 각 10개 p50·p95 |
| 운영 Pod 최대 RSS | 부하 전 baseline → 동시 미리보기 처리 중 최고점 | baseline 대비 peak delta |
| 운영 장애율 | 전체 미리보기 요청 대비 실패 요청 | 7일 단위 실패율 · 원인 코드별 비율 |

현재 수치는 동일 머신·동일 부하의 로컬 프로세스 비교값이며, 운영 지표는 실제 Kubernetes·MinIO·파싱엔진 연결 환경에서 별도로 검증합니다.
