> **담당 범위:** 사용 이벤트 수집부터 일별 집계·정산, 호출 전 한도 판단, 대시보드 조회까지 데이터 흐름을 설계했습니다. 조회·비교·한도 API, 화면, Excel 내보내기와 인보이스를 직접 구현하고 공통 Kafka 인입·집계 기반에 연결했습니다.

## 문제 원인 · 해결 목표

- **상황:** 원본 사용 기록을 반복 집계하면 조회가 느렸고, 서비스가 추가될 때마다 요청·화면·정산 기준을 함께 수정해야 했습니다.
- **목표:** 실시간 한도 제어와 대시보드 조회를 연결하면서 과거 청구 기준을 유지하고, 비교 조회와 화면의 반복 요청을 줄여야 했습니다.

## 해결 과정

1. **요청 전 한도 확인** — 제가 만든 한도 API는 직원이 질문을 보낼 때 조직과 개인의 누적 사용액을 확인하고, 한도에 도달한 호출을 차단합니다.
2. **사용 기록과 비용 집계** — AI 호출이 끝나면 공통 시스템이 사용량을 기록합니다. 사용 당시의 가격과 환율로 계산한 일별 집계를 조회 API에 연결했습니다.
3. **계열사별 비교** — 제가 만든 조회 API는 관리자가 고른 기간과 직전 기간의 계열사별 사용량을 한 번에 반환합니다. 대시보드와 엑셀 내보내기는 같은 조회 결과를 사용합니다.

## 결과

- **사용자 요약 조회 p95**는 228.665ms에서 0.383ms로 줄었습니다. 사용자 한 명의 원본 10,000건을 매번 합산하던 조회가 일별 요약 한 건을 읽습니다.
- **계열사 비교 요청:** 약 34회 → 1회. 미리보기·Excel·PDF가 같은 조회·계산 기준을 사용하도록 연결했습니다.

### 검증 조건 · 현재 한계

일별 요약 네 종류를 미리 생성하고 저장하는 데 한 차례 측정에서 26.924초가 들었습니다. 별도로 타이머 시작 후 MongoDB에 카운터가 처음 보인 시점은 60.052초였습니다. 조회 시간은 선계산·HTTP·인증을 제외한 서버 구간에서 측정했습니다.

### 후속 구현

백오피스에서는 조직과 기간을 선택해 신규·기존 에이전트의 토큰 사용량을 비교하고, 상세 화면에서도 같은 조건을 유지합니다. 한도 제어에서는 Redis 누계가 없을 때 MongoDB를 조회합니다. 두 저장소 모두에서 사용액을 확인할 수 없으면 한도 강제 모드에서 호출을 중단합니다.

일부 텍스트 요청에 최대 비용을 먼저 예약하고 종료 뒤 실비를 정산하는 경로도 구현했습니다. 기록 시점에는 기본 비활성 상태였고 통합 테스트 실행과 운영 적용은 확인 전이었습니다.

인보이스 후속 브랜치에서는 서버가 정산 문서와 버전을 만들고 다운로드 시 권한을 다시 확인합니다. 같은 Chromium 프로세스에서 요청마다 새 컨텍스트를 열자, 로컬 9쪽 합성 문서의 warm PDF 변환 중앙값이 1.53초에서 0.66초로 줄었습니다. 인증과 네트워크를 제외한 변환 시간입니다.
