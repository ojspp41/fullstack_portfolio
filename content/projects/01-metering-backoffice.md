# 호출 한 건을 비용과 운영 지표로 바꾸는 미터링 파이프라인

**Go · Kafka · MongoDB · Redis · React Query · ExcelJS**

### 한 줄 요약

AI 호출 전 한도를 제어하고, 호출 후 사용 기록을 일별 요약으로 집계해, 가격이 바뀐 뒤에도 당시 비용을 재현할 수 있는 백오피스 흐름을 연결했습니다. 화면과 API는 새 서비스가 추가돼도 서비스별 코드를 반복 수정하지 않는 동적 계약으로 바꿨습니다.

### S — 원본 사용 기록만으로는 운영할 수 없었다

AI 서비스가 늘어나면서 관리자는 조직·사용자·에이전트·서비스별 사용량과 비용을 조회하고 엑셀로 내려받아야 했습니다. 하지만 원본 기록 수백만 건을 요청마다 다시 합산하면 조회가 느렸고, 현재 가격만 저장하면 과거 청구를 재현할 수 없었습니다. 서비스가 추가될 때마다 `web_tokens`, `odin_tokens` 같은 필드를 늘리는 방식도 프론트와 백엔드를 함께 수정하게 만들었습니다.

이 문제는 대시보드 하나를 만드는 작업이 아니라 다음 흐름을 하나의 계약으로 연결하는 작업이었습니다.

```text
AI 호출 요청
  → Redis 사용 한도 확인
  → AI 호출 및 사용 기록 생성
  → Kafka 전달
  → 일별 요약 집계(upsert)
  → 사용 시점의 가격·환율 적용
  → 조회·비교 API
  → 대시보드·엑셀
```

### T — 네 가지 경계를 함께 맞췄다

1. Kafka에서 기록이 재전달돼도 비용이 중복되지 않는 집계
2. 원본 데이터 증가가 화면 조회 시간에 직접 번지지 않는 요약 구조
3. 가격·환율 변경 뒤에도 과거 비용을 같은 기준으로 재현하는 정산
4. 신규 서비스가 예고 없이 추가돼도 API와 화면이 자동으로 받아들이는 응답 계약

### 담당 범위

**직접 구현**

- 미터링 조회 API: 필터 6종·페이지 처리
- 사용 한도 제어 API: 요금제별 한도 조회와 Redis 카운터 기반 초과 호출 차단·경고
- 계열사 비교 API: 현재·이전 기간의 토큰·활성 사용자·Top 에이전트·모델 분포 일괄 반환
- `source_usages[{source, total_tokens, charge_amount}]` 응답 계약과 유료 API 비용 합산
- 대시보드·목록 공통 훅·URL 필터 상태·ExcelJS 다중 시트 내보내기
- 알 수 없는 서비스의 필터·색상·범례·그래프·엑셀 자동 생성과 구형 응답 호환
- Kafka 기반 미터링 이벤트 인입과 소비 실패 처리
- 일배치 사전 집계와 복합 키 upsert
- 가격·환율 이력 버전 관리와 청구 시점 재현

미터링 기능은 이벤트 인입부터 집계·정산·조회·화면 소비까지 직접 구현했습니다. 다만 공통 Kafka 기반 기능 전체가 아니라 미터링 이벤트의 생산·소비·실패 처리와 집계로 이어지는 범위로 한정해 설명합니다.

### 전체 구조에서 가장 중요한 연결

공통 Kafka 소비부는 핸들러 성공 후 메시지를 완료 처리합니다. 기본 `retry_uncommitted` 정책에서는 실패한 메시지를 완료 처리하지 않아 다음 세션에서 재전달될 수 있습니다. 그래서 일별 집계는 `사용자·조직·API 키·서비스·날짜` 복합 키로 upsert해 같은 범위를 다시 실행해도 같은 요약 결과로 수렴해야 합니다.

가격과 환율은 `valid_from`, `valid_to` 기간으로 이력을 보존합니다. 현재 가격을 과거 기록에 일괄 적용하지 않고 사용 시점에 유효했던 버전을 찾아야 당시 청구를 다시 계산하고 검증할 수 있습니다.

### 실시간 한도 판정과 일별 대시보드 집계를 분리했다

사용 기록은 Kafka로 받은 즉시 MongoDB `metering` 컬렉션에 원본으로 저장합니다. 한도 판정 때마다 원본을 전부 합산하면 느리기 때문에 사용자·조직별 누적 청구액은 Redis에 이벤트마다 반영하고, Gateway가 다음 호출 전에 조직 한도와 개인 한도를 순서대로 확인합니다.

한도용 MongoDB 문서인 `user_usage_period`, `organization_usage_period`는 상세 사용 내역을 중복 저장하지 않고 사실상 `charge_amount` 누적액과 식별 키·생성/수정 시각만 보존합니다. Redis에는 즉시 반영하고 MongoDB 카운터에는 메모리에 모은 증가분을 현재 설정 기준 60초마다 일괄 반영해, Redis 키 유실이나 장애 때 사용할 복구 값을 유지합니다. 매일 원본 기준으로 카운터를 다시 계산해 Redis와 MongoDB의 오차를 보정합니다.

대시보드 요약은 사용자·조직·API 키·출처·날짜와 모델·함수·API 사용량을 여러 단계로 분류·합산하는 무거운 작업입니다. 이를 60초마다 반복하면 같은 미완료 일자의 원본 범위를 계속 다시 읽고 네 종류의 요약본을 갱신해야 하므로, 초 단위 최신성이 필요하지 않은 화면 요구에 맞춰 일배치로 분리했습니다.

#### 왜 Kafka·Redis·MongoDB를 나눠 사용했나

공식 문서가 세 기술의 조합을 정해 준 것은 아닙니다. 각 문서가 설명하는 주된 사용 목적을 우리 요구사항에 대응시켜 역할을 나눈 설계입니다.

| 기술 | 공식 문서가 설명하는 적합한 상황 | 우리 요구사항과 선택 이유 | 이 기술에 맡기지 않은 역할 |
|---|---|---|---|
| Kafka | 이벤트 스트림 발행·구독, 내구성 있는 저장, 실시간 또는 사후 처리([공식 문서](https://kafka.apache.org/documentation/)) | AI 호출 서비스와 미터링 처리를 분리하고, 처리 실패 시 사용 이벤트를 다시 전달받을 수 있게 함 | 현재 누적 금액을 요청마다 조회하는 역할 |
| Redis | Rate Limiting과 빠른 캐시, `INCR` 계열 명령을 이용한 원자적 카운터([사용 사례](https://redis.io/docs/latest/develop/use-cases/), [`INCR` 문서](https://redis.io/docs/latest/commands/incr/)) | 다음 AI 호출 전에 사용자·조직별 현재 누적 청구액을 빠르게 확인하고 한도 초과 요청을 통제함 | 상세 사용 내역과 최종 청구 근거의 영구 보관 |
| MongoDB | 접근 방식에 맞춘 문서 모델링과 여러 문서의 분류·그룹·합산([데이터 모델링](https://www.mongodb.com/docs/manual/data-modeling/), [집계](https://www.mongodb.com/docs/manual/aggregation/)) | 호출별 상세 원본을 장기 보관하고 일별·조직별·청구 주기별 결과를 다시 계산할 기준으로 사용함 | 매 요청 경로에서 원본 전체를 합산하는 실시간 한도 판정 |

Redis를 선택한 핵심 이유는 단순히 빠른 저장소가 필요해서가 아니라 **실시간 통제 경로**가 필요했기 때문입니다. 미터링 서비스는 사용 이벤트의 금액을 계산한 뒤 `IncrByFloat`로 사용자 키와 조직 키를 즉시 증가시키고, Gateway는 다음 호출 전에 이 값을 한도와 비교합니다. 반대로 Kafka와 MongoDB는 **증거 경로**를 구성합니다. Kafka가 사용 사실을 전달·재처리할 수 있게 하고 MongoDB가 상세 원본을 남기므로, Redis 값이 유실되거나 어긋나도 원본을 기준으로 복구할 수 있습니다.

```go
amount := computeRecordCharge(record, model, api, fx, s.log)
// ...
newVal, err := s.services.Redis.IncrByFloat(ctx, key, amount)
```

이 코드에서 사용 시점의 청구액을 계산한 뒤 사용자·조직 누적값을 건별로 증가시킵니다. 즉 Redis의 책임은 청구 원본 보관이 아니라 다음 요청의 허용·차단에 사용할 현재값 유지입니다.

세 기술을 나눈 대가도 있습니다. Kafka에는 소비 지연과 재전달에 따른 중복 방어가 필요하고, Redis에는 키 유실과 원본의 일시적 오차가 생길 수 있으며, MongoDB 원본 집계는 데이터 증가에 따라 무거워집니다. 그래서 Kafka 메시지 좌표 기반 중복 방지, MongoDB 카운터의 60초 단위 반영, 매일 원본 기준 대조, 일별 요약 사전 계산으로 각각의 약점을 보완했습니다. 다만 공통 Kafka 소비부의 기본 재전달 정책은 코드로 확인했지만 미터링 소비자의 실제 연결 정책은 별도 확인이 필요합니다.

**입에 붙는 답변:** 사용량 시스템은 실시간 통제와 청구 증거의 요구가 달라 역할을 나눴습니다. Kafka는 사용 이벤트를 서비스 사이에서 분리해 전달하고 실패 시 다시 처리하기 위해, MongoDB는 상세 원본과 청구 근거를 장기 보관하고 집계하기 위해 사용했습니다. Redis는 다음 호출 전에 사용자·조직의 누적 청구액을 빠르게 비교해 한도를 통제하기 위해 사용했습니다. Redis가 최종 원본은 아니므로 MongoDB 카운터에 60초마다 반영하고 매일 원본과 대조했습니다. 다만 비용이 호출 후 확정되므로 동시 요청이나 처리 지연만큼 한도가 조금 초과될 수 있습니다.

# 데이터가 늘어도 조회 비용과 수정 범위를 통제하는 구조

### A — 화면 모양에서 API 계약을 역설계했다

대시보드가 필요한 값은 단순 총합이 아니었습니다. 현재·이전 기간, 계열사, 서비스, 모델, 활성 사용자, Top 에이전트를 같은 기준으로 비교해야 했습니다. 이를 브라우저의 반복 요청으로 조합하지 않고 서버가 한 번에 반환하도록 비교 API를 만들었습니다.

- MongoDB `$switch`로 현재·이전 기간을 구분
- `$facet`으로 서비스·모델·활성 사용자·Top 에이전트 집계를 한 요청 안에서 수행
- 전사 활성 사용자는 `기간+사용자 ID`로 묶어 여러 서비스를 사용한 한 사람을 한 명으로 계산
- 계열사별 활성 사용자는 `기간+조직 ID+사용자 ID`로 계산
- 에이전트 ID는 집계 후 한 번에 이름으로 변환해 반복 조회 방지

계열사 수에 비례해 늘던 브라우저 요청은 약 34회에서 1회로 줄었습니다. 서버 내부 조회도 계열사 수와 관계없이 MongoDB Aggregate 3회와 에이전트 이름 조회 최대 1회로 제한했습니다.

### A — 서비스명을 데이터로 취급했다

기존 응답은 `web_tokens`, `odin_tokens`처럼 서비스명이 필드에 박혀 있었습니다. 이를 아래 배열 계약으로 바꿨습니다.

```json
{
  "source_usages": [
    { "source": "atlas", "total_tokens": 120000, "charge_amount": 15300 },
    { "source": "lens", "total_tokens": 0, "charge_amount": 8200 }
  ]
}
```

모델 사용료와 유료 API 사용료를 source별로 합산하며, 토큰이 없는 API 전용 서비스도 `charge_amount`가 있으면 결과에서 보존합니다. 프론트는 응답에서 서비스 목록을 수집하고 이름 기반 색상을 만들어 필터·범례·누적 막대·엑셀에 자동 반영합니다.

배포 중 계약이 바뀌는 위험은 프론트 정규화 계층으로 줄였습니다. 신형 프론트가 구형 고정 필드와 신형 배열을 모두 처리하게 만든 뒤 백엔드를 배포할 수 있어 순차 배포가 가능합니다.

### A — 조회부터 파일까지 하나의 흐름으로 구현했다

사용자가 내보내기를 누르면 미터링 API가 필터 6종과 페이지 조건에 맞는 데이터를 제공하고, 브라우저가 ExcelJS로 요약·상세 시트를 생성합니다. 진행·완료·실패 상태와 파일 다운로드까지 화면에서 처리해 수작업 정산 자료 작성을 줄였습니다.

### R — 검증 결과

측정 조건: 재현 데이터 300만 건 · 실제 MongoDB · 실제 집계 파이프라인

| 지표 | 결과 |
|---|---|
