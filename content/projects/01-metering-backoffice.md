## 전체적인 아키텍처

![사용량·비용 미터링 백오피스 — 전체 구조](/diagrams/metering.png)

*구조 그림을 선택하면 원본 크기로 볼 수 있습니다.*

> **담당 범위:** 백오피스 화면·조회/비교 API·사용 한도 API·Excel·인보이스를 직접 구현했습니다. Kafka 인입, 일배치, 가격·환율 이력 기반은 설계를 이해하고 연동한 범위로 설명합니다.

## 문제 원인 · 해결 목표

- **상황:** 원본 사용 기록을 반복 집계하면 조회가 느렸고, 서비스가 추가될 때마다 요청·화면·정산 기준을 함께 수정해야 했습니다.
- **목표:** 실시간 한도 제어와 대시보드 조회를 연결하면서 과거 청구 기준을 유지하고, 비교 조회와 화면의 반복 요청을 줄여야 했습니다.

## 해결 과정

1. 실시간 호출 한도는 Redis 카운터와 한도 API로 판정하고, 대시보드는 일별 요약을 조회하도록 연결했습니다. 원본 상세와 요약의 목적을 나눴습니다.
2. 조회·비교 API의 필터·페이지 처리와 `source_usages` 응답 계약을 구성했습니다. 현재·이전 기간과 조직별 비교 데이터를 한 응답으로 받아 화면에서 재사용했습니다.
3. 같은 계약을 대시보드·ExcelJS 내보내기·인보이스에 연결했습니다. 인보이스 미리보기와 PDF는 같은 데이터와 금액 계산을 사용하도록 구성했습니다.

## 결과

- **300만 건 재현 데이터:** 조회 1,970ms → 2.6ms, 약 750배 개선한 기록을 확인했습니다.
- **계열사 비교 요청:** 약 34회 → 1회. 미리보기·Excel·PDF가 같은 조회·계산 기준을 사용하도록 연결했습니다.

### 검증 조건 · 현재 한계

750배는 재현 데이터 조회 결과입니다. 모든 사용자 요청의 운영 지연 개선율로 확대하지 않습니다. 별도 100만 건 로컬 비교의 요약 조회 중앙값은 228.665ms → 0.383ms이며, 집계 작업은 26.924초와 60.052초의 재실행 기록으로 건수·비용 수렴을 확인했습니다. 서로 다른 데이터·작업의 측정값을 하나의 성능 지표로 합치지 않습니다.

전체 Kafka 인입·실패 처리·집계 엔진을 단독 구축했다는 주장 대신, 본인이 맡은 조회·한도·화면 계약과 공통 파이프라인 연동을 구분합니다.
